# Phase 06 Jobs Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans task-by-task. Production behavior changes follow TDD: first a failing unit/pgTAP/runtime/browser test, then the minimum implementation, then full regression verification.

**Goal:** Turn a fake-paid proposal into a schedulable, auditable Job that can proceed from confirmation through execution, rescheduling, scope changes, completion, cancellation, dispute and no-show without double booking or leaking private location data.

**Architecture:** PostgreSQL remains the source of truth. Job state changes, schedule acceptance, conflict prevention, availability checks, slot holds and scope-price changes are performed through transactional `SECURITY DEFINER` RPCs with fixed `search_path`; authenticated clients retain read-only direct table access under RLS. The payment boundary stays provider-agnostic: `FakePaymentProvider` is an adapter, not economic truth. The web layer calls typed server helpers/actions and renders mobile-first job views.

**Tech Stack:** Next.js App Router, TypeScript, Supabase PostgreSQL/Auth/RLS, pgTAP, PostGIS, Vitest, Playwright.

**Authoritative spec:** `CHANGAS_MASTER_PLAN.md` — Phase 06 plus Scheduling requirements (§14), Scope changes and Cancellation/no-show requirements.

**Approved baseline:** Phase 05 final closure `4ef03e6cd56c4c697535b7abb5f161c94552135d`.

## Global Constraints

- Money remains integer minor units; never floating point.
- No real payment provider in Phase 06.
- Accepted proposal snapshots remain immutable.
- Job state transitions are server-enforced and auditable.
- Realtime/chat history is not economic truth.
- Exact private address is never public and is released only in the confirmed in-person job context to participants.
- No direct authenticated `INSERT`/`UPDATE`/`DELETE` on economic tables.
- Slot availability is revalidated server-side; the client view is never authoritative.
- Do not implement automatic recurring bookings. “Recurring” in this phase means provider availability rules by weekday/time/timezone.
- Preserve Phase 05 generic `PaymentProvider` / `apply_payment_result` architecture.
- STOP after Phase 06. Reviews/reputation are Phase 07; real payments are Phase 11.

### Task 3: Recurring provider availability

**New authoritative requirement previously missing from this implementation plan.**

**Produces:** provider-owned recurring rules containing:

- weekday;
- local start/end time;
- timezone;
- active/paused state;
- audit timestamps.

Availability rules are not recurring bookings. They define when fixed-slot bookings may be accepted/held.

**Must prove:** provider can maintain only their own rules; invalid timezone/time ranges fail; when active rules exist, an out-of-rule fixed slot cannot be held/confirmed.

### Task 4: Availability exceptions / blocks

**New authoritative requirement previously missing from this implementation plan.**

**Produces:** provider-owned unavailable intervals for personal time, vacation/manual blocks and equivalent exceptions. Confirmed Changas jobs remain separate booking claims but participate in the same availability decision.

**Must prove:** an exception overlapping a requested fixed slot makes it unavailable; outsider cannot inspect private provider scheduling data; a provider cannot mutate another provider’s blocks.

### Task 5: Temporary slot hold abstraction

**New authoritative requirement previously missing from this implementation plan.**

**Produces:** PostgreSQL-safe temporary fixed-slot holds during payment, with expiry and deterministic/idempotent identity. Do not overbuild distributed locks; use transaction/advisory locking plus constraints/checks where sufficient.

**Must prove:** two active holds cannot claim the same provider interval; an expired/released hold does not block later booking; successful conversion cannot create two Jobs; pending fake payment can retain its hold; failed fake payment releases it safely.
